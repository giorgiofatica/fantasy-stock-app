# If Giorgio connects Supabase's official MCP server to Claude in read-only mode, scoped to one project, for a Claude Data dashboard: what can it reach, and what is the tightest configuration that still allows read-only counts?

Asked by: the Planner (for Giorgio, after his ruling "yes as a trial, do the security read first") on 2026-11-10, with two additions from the Orchestrator · Researcher session: Researcher (quizzical-lumiere-85ec0f) · Model: Opus 5.5

Scope: this is the **external** half (the connector, Supabase's platform, Anthropic). The Planner covers the repo half: what a read-only SQL user could reach in our own tables and functions. Every source below was read on 2026-11-10.

## Short answer
Read-only mode does not narrow what the connector can see. It runs SQL as Supabase's `supabase_read_only_user`, which has `pg_read_all_data` **and `BYPASSRLS`**: it reads every table in every schema, `auth.users` included, and ignores our RLS. Writes are stopped by Postgres, not by the connector, but it isn't documented whether a query can switch its own transaction to read-write. The default directory connector is not acceptable. A custom connector set to `project_ref` + `read_only=true` + `features=database`, with every tool except `execute_sql` blocked, is acceptable for a count-only trial only if a non-prod test first proves the role **cannot** read `vault.decrypted_secrets`. Before real players, it needs a narrower role than Supabase's, and this connector can't supply one.

## What this means for Stockpile
- **"Read-only" is about writes, not about what it can see.** The connector can see what `service_role` sees and more (`auth`, `cron`, `net`, migration history), past every RLS policy in `supabase/migrations/`. Our RLS work, the profile-visibility rule (2026-10-08) and the lock-down rule don't apply to this role (findings 3, 6, 8).
- **Vault holds real secrets even while prod holds only test accounts.** Per CLAUDE.md, the cron jobs read keys from `vault.decrypted_secrets`. If test 2 shows the read-only role gets plaintext, one stray `SELECT` (by mistake, or from an injected instruction) puts a live server key into a Claude conversation. That's a rotation event under the repo's secret-handling rule. This is why the trial hinges on test 2, not on the test-account data.
- **The writes question meets the Planner's half.** If test 3 shows a query can turn on read-write, every `SECURITY DEFINER` function that still has PUBLIC `EXECUTE` becomes a write path. That's the same `proacl` audit CLAUDE.md describes (finding 11).
- **Account deletion.** Rows Claude reads stay in conversation history under Anthropic's retention (finding 23). Count-only queries avoid this. Any query that returns `auth.users` or profile rows would put deleted players' data out of reach of our deletion. *(Inference.)*
- **`get_edge_function` returns our function source** (finding 13). The repo holds the same code, so this matters less, but it's still reason to leave the Edge Functions group off.

### Hands-on tests: on a **non-prod** Supabase project only, never prod
Connect it exactly as proposed: custom connector, `?project_ref=<test ref>&read_only=true&features=database`. Then run through `execute_sql`:
1. `SELECT current_user, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user;` This settles which role it runs as and whether it bypasses RLS.
2. Create one dummy Vault secret, then `SELECT name, decrypted_secret FROM vault.decrypted_secrets;` Plaintext coming back means the trial on prod is off. Also `SELECT count(*)` on `auth.users`, `auth.identities`, `cron.job`, `net._http_response` and `supabase_migrations.schema_migrations`.
3. Writes: a plain `INSERT` into a scratch table, then the same after `SET TRANSACTION READ WRITE;`, then after `SET default_transaction_read_only = off;`. All three must fail.
4. Create a `SECURITY DEFINER` function that inserts a row, with PUBLIC `EXECUTE`, then call it the three ways in test 3. It must fail.
5. Pass another project's id to a tool. It must be refused.
6. Try `deploy_edge_function` and `create_branch`. They should be absent with `features=database`; check what read-only does if they're present.
7. Check that the claude.ai tool list shows only the Database group, with no notebook tools.
8. Check that the URL parameters survive in the custom connector: test 1's role and test 3's failures prove `read_only` took effect.
9. Note the OAuth consent screen's scopes and where the grant appears for revocation; revoke it and confirm the connector stops working.
10. Build one Claude Data dashboard on `execute_sql` with a single `SELECT count(*)` and confirm it renders.

## Recommendation
*This is advice, not a decision. The Orchestrator reviews it, and Giorgio decides.*

**Is the default connector acceptable for a count-only trial while prod holds only test accounts? No.**
- The one-click directory connector, without parameters, gets org-wide write-scoped access with every tool group on.
- That includes `apply_migration` and `deploy_edge_function`, plus `execute_sql` with no read-only flag.

**What is acceptable for the trial, if tests 1–4 pass on a non-prod project:**
1. **A custom connector** at `https://mcp.supabase.com/mcp?project_ref=<prod ref>&read_only=true&features=database`.
2. **Block every tool except `execute_sql`** in Customize > Connectors.
3. **Never "Always allow" `execute_sql` in chat**, so each query is approved by eye.
4. **Datasets are `count(*)` or `GROUP BY` totals only:**
   - no column from `auth.*`, `vault.*`, `cron.*` or `net.*`;
   - no text a player typed.
5. **Not shared.** Only Giorgio views it.
6. **Revoke it** at the end of the trial.

If request headers are available, a project-scoped PAT with only `database_read` in place of OAuth narrows the credential further.

**If test 2 returns plaintext secrets, or test 3/4 can write: don't connect to prod at all, even for the trial.** Use a non-prod copy, or a file export of counts (below).

**What must change before real players.** This connector's role reads everything and can't be narrowed (finding 8), so before real players it should be replaced, not tuned. The options to plan:
- **(a) Own the connection.** A Postgres connector of our own (or an edge function) that logs in as a role we create. That role gets SELECT on a few aggregate views only: no `auth`, no Vault, no BYPASSRLS.
- **(b) No live connection.** A scheduled job exports aggregate counts to a file, and the Data dashboard reads the file. Nothing in Claude can reach the database.

(b) is the tightest; (a) is live but needs building and a security review. Both are the Planner's and Orchestrator's to scope.
